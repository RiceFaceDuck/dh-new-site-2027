# Backoffice Development Guidelines

เมื่อมีการพัฒนาหรือเพิ่มฟีเจอร์ใหม่ใน **ระบบหลังบ้าน (dh-backoffice-react)** ห้ามลืมทำสิ่งเหล่านี้เด็ดขาด:
1. **ต้องเพิ่มคำอธิบายและการสอนการใช้งานเข้าไปใน UI ของระบบด้วยทุกครั้ง** (In-App Documentation)
2. คู่มือ/คำอธิบายต้องประกอบไปด้วย:
   - **ตำรา / คำอธิบาย**: อธิบายว่าฟีเจอร์นี้คืออะไร ใช้ทำอะไร
   - **วิธีการใช้งาน (How-to)**: อธิบายเป็นขั้นเป็นตอน
   - **เทคนิคการใช้งาน (Tips & Tricks)**: บอกเทคนิคที่ทำให้ใช้งานได้ง่ายหรือเร็วขึ้น (เช่น Shortcut Keys)
   - **ตัวอย่างผลลัพธ์ (Expected Results)**: แสดงตัวอย่างหรือคำเตือนที่ชัดเจนก่อนผู้ใช้จะกดยืนยันการทำงาน

ให้คำนึงเสมอว่าผู้ใช้งานมีหลายระดับ (Staff ใหม่, Manager) การสร้าง UI ต้องมาพร้อมคำอธิบายในตัวเสมอ (เช่น Guide Modal, Tooltip, Help Panel)
**ข้อกำหนดพิเศษสำหรับ React Components:** ให้เรียกใช้งาน Component `<GuidePanel />` (จาก `src/components/common/GuidePanel.jsx`) เสมอ เมื่อมีการสร้างหน้าต่าง, Modal, หรือฟีเจอร์ใหม่ที่ซับซ้อน เพื่อรักษามาตรฐาน UI ของคู่มือ (In-App Documentation) ให้เป็นไปในทิศทางเดียวกัน

# AI Core Directives (DH Notebook)

เพื่อให้ AI สามารถทำงานในโปรเจกต์ได้อย่างมีประสิทธิภาพสูงสุด กรุณายึดถือกฎต่อไปนี้ในทุกๆ การสนทนาและการพัฒนา:

1. **Auto-Refactor & SRP:** หากพบว่าไฟล์มีขนาดใหญ่, Logic ซับซ้อน หรือทำหลายหน้าที่ (Spaghetti Code) ให้ทำการ Extract Component, Custom Hook หรือ Service ออกมาใหม่ทันที โดยยึดหลัก Single Responsibility Principle
2. **Firebase Optimization:** การเขียนโค้ดต้องคำนึงถึงความสมดุลระหว่าง "ประสิทธิภาพ/ความเร็ว" และ "การประหยัดโควต้า Reads/Writes" อย่างเคร่งครัด
3. **Strict Data Relations:** ก่อนลบหรือปรับปรุงโครงสร้างข้อมูล ให้ตรวจสอบความสัมพันธ์ (Relations) กับเอกสารอื่นๆ เพื่อป้องกันปัญหาข้อมูลกำพร้าหรือระบบพัง
4. **Premium UX/UI:** ให้ความสำคัญกับความสวยงาม นำเสนอและประยุกต์ใช้ลูกเล่นที่ทำให้ระบบดูทันสมัยและใช้งานง่าย มุ่งสู่ความรู้สึก "High Quality System" เสมอ
5. **Safe Editing:** แก้ไขโค้ดเฉพาะส่วนที่ได้รับมอบหมาย ห้ามแก้ไขฟังก์ชันที่ไม่เกี่ยวข้อง และห้ามลบโค้ดเดิมที่ยังทำงานได้หรือไม่ได้สั่งให้ปรับปรุง
6. **Audit Log Awareness:** การเปลี่ยนแปลงข้อมูลสำคัญโดยเฉพาะที่เกิดจากผู้ใช้งาน (Staff/Manager) จะต้องมีระบบจัดการเพื่อบันทึกประวัติ (History Log) ด้วยเสมอ
7. **Future Backlog Rule:** เมื่อผู้ใช้สั่งให้บันทึกแผนงานในอนาคต (Future Backlog / คลังไอเดียที่พับเก็บไว้) ห้ามนำไปบันทึกปะปนกับ "รายการเตรียมการพัฒนา (Backlog)" หรือเขียนรายละเอียดลงในเอกสารแนวคิด ให้เอาเฉพาะหัวข้อและคำอธิบายสั้นๆ ไปบันทึกแยกในหมวด "แผนงานในอนาคต / คลังไอเดีย (Future Backlog & Ideas)" ในไฟล์ `TODO.md` เพื่อเป็นบันทึกเรียกดูไอเดียเท่านั้น
8. **Interactive Choices (Choice-First Questioning):** เมื่อต้องการถามผู้ใช้เพื่อความชัดเจน, ขอข้อสรุปแนวทางพัฒนา, การตัดสินใจในงานออกแบบ หรือชื่อหมวดหมู่ต่างๆ ให้เอเจนต์ตั้งคำถามและนำเสนอตัวเลือกเป็น "ช้อยส์ (Choices)" เพื่อให้ผู้ใช้เลือกผ่านการเรียกใช้เครื่องมือ `ask_question` เสมอ เพื่อประหยัดเวลาและทำให้ได้ข้อสรุปที่รวดเร็ว
9. **Concise Communication Style (Conversational & Direct):** ในการโต้ตอบ พูดคุย หรือเสนอแผนงานกับผู้ใช้ ให้เน้นสื่อสารแบบกระชับ สั้น ตรงประเด็น และอธิบายเพียงเล็กน้อยเหมือนการพูดคุยกันทั่วไป ห้ามพิมพ์ข้อความยาวเป็นเรียงความหรือเขียนเนื้อหาแบบตำราเรียนเด็ดขาด
12. **Ultra-Concise Responses & Artifacts:** เอเจนต์จะต้องอธิบายผลลัพธ์, แผนงาน (Implementation Plan), สรุปผลลัพธ์ (Walkthrough), และการโต้ตอบพูดคุยทั้งหมดแบบ "สั้น กระชับ แต่เข้าใจง่าย (ตรงประเด็นที่สุด)" ห้ามเขียนเยิ่นเย้อเด็ดขาด
13. **Context-Aware Recommendations:** หากผู้ใช้ถามว่า "อยากแนะนำอะไรไหม" หรือ "อยากทำอะไรเพิ่มเติมไหม" ให้เสนอแนะงานที่ **เกี่ยวข้องกับเนื้องานที่เพิ่งทำเสร็จไป (Related Tasks)** หรือส่วนงานเดิมเป็นหลัก เพื่อให้งานในส่วนนั้นสมบูรณ์ที่สุดก่อนข้ามไปทำเรื่องอื่น
14. **Auto Image Compression:** เมื่อมีการพัฒนาระบบหรือเขียนโค้ดที่เกี่ยวข้องกับการ "อัปโหลดรูปภาพ" (ไปยัง Firebase Storage หรืออื่นๆ) จะต้องเขียนโค้ดให้ทำการบีบอัด (Compress/Resize) ไฟล์ภาพให้มีขนาดเล็กที่สุดอัตโนมัติก่อนอัปโหลดเสมอ โดยที่ยังคงความคมชัดไว้ (เช่น ใช้ `browser-image-compression`)

# AI Autonomy & Workflow Permissions

เพื่อให้การทำงานคล่องตัวและรวดเร็วขึ้น AI ได้รับอนุญาตให้ดำเนินการดังต่อไปนี้ได้อย่างอิสระ:
1. **Testing & Verification:** อนุญาตให้ใช้เวลาในการ "ตรวจสอบผลลัพธ์" (Testing) อย่างมีอิสระได้เสมอ เมื่อมีการสั่งให้ตรวจสอบหรือทดสอบระบบ
2. **Skill Management:** อนุญาตให้อัปเดตไฟล์ `SKILL.md` ได้เสมอ เพื่อพัฒนาความสามารถ
3. **Architecture Updates:** อนุญาตให้อัปเดตเอกสาร `ARCHITECTURE.md` ได้เสมอ เมื่อมีข้อมูลเพิ่มเติม
4. **Audit Updates:** อนุญาตให้อัปเดตเอกสาร `Audit Checklist.md` ได้เสมอ
5. **Concept Notes Updates:** อนุญาตให้อัปเดตเอกสาร `CONCEPT_NOTES.md` ได้เสมอ เมื่อได้รับแนวคิดหรือมีการออกแบบใหม่จากผู้ใช้
6. **Schema Updates:** อนุญาตให้อัปเดต Schema ในโฟลเดอร์ `Schema Key` ได้เสมอ เพื่อความแม่นยำในการรับ-ส่งงาน
7. **Task Board Updates:** อนุญาตให้อัปเดตไฟล์ `TODO.md` ได้เสมอ เมื่อได้รับแผนงานใหม่
8. **Quota Estimation Updates:** อนุญาตให้อัปเดตข้อมูลการจำลองและคำนวณโควต้าในไฟล์ `FIRESTORE_QUOTA_ESTIMATION.md` ได้เสมอ
9. **Plan & Task Separation:** เมื่อมีการวางแผน ให้แยก Artifact ระหว่าง Plan (แผนงานรวม) และ Task (ตารางงานย่อย) อย่างชัดเจน
10. **Post-Task Evaluation:** เมื่อทำงานตามแผนเสร็จสิ้น จะต้องมีการประเมินผลลัพธ์การใช้โควต้า อ่าน-เขียน (Reads/Writes) ของ Firebase เสมอ โดยบันทึกลงใน `FIRESTORE_QUOTA_ESTIMATION.md`
11. **Critical Warning Logging (CAUTION!):** หากพบสถานการณ์ที่มีความเสี่ยงสูง (เช่น Breaking Changes, การแก้ระบบโครงสร้างหลัก) และมีการตั้งค่าแจ้งเตือน [!CAUTION] ให้เอเจนต์นำหัวข้อนั้นไปบันทึกสั้นๆ ไว้ในไฟล์ `SYSTEM_CAUTIONS.md` ที่ root folder เสมอ เพื่อแจ้งเตือนเอเจนต์คนอื่นในอนาคต

# File Modification Summary Style
เมื่อเอเจนต์ดำเนินการจัดการไฟล์โค้ดหรืออัปเดตไฟล์เสร็จสิ้น เอเจนต์จะต้องรายงานสรุปรายชื่อไฟล์ที่เกี่ยวข้องให้ผู้ใช้งานทราบด้วยรูปแบบ (Visual Layout) ที่ชัดเจนและสวยงาม โดยมีรูปแบบดังนี้:

1. ใช้หัวข้อนำด้วยอิโมจิโฟลเดอร์สีเหลือง: `📁 สรุปไฟล์ที่เกี่ยวข้องกับการอัปเดตครั้งนี้`
2. แสดงรายการในรูปแบบลำดับหมายเลข (1, 2, 3...) โดยมีอิโมจิที่แสดงถึงประเภทของไฟล์เสมอ:
   - ไฟล์ React JSX/TSX: ใช้รูปอะตอม `⚛️` (เช่น `1. ⚛️ App.jsx : ...`)
   - ไฟล์ JavaScript (JS) หรือ TypeScript (TS): ใช้รูปสี่เหลี่ยมสีเหลือง `🟨` (เช่น `2. 🟨 inventoryService.js : ...`)
   - ไฟล์ Markdown (MD): ใช้รูปสี่เหลี่ยมสีน้ำเงิน `🟦` (เช่น `3. 🟦 Audit Checklist.md : ...`)
   - ไฟล์ CSS หรือ Stylesheet: ใช้รูปแปรงทาสี `🎨` (เช่น `4. 🎨 index.css : ...`)
3. บันทึกคำอธิบายสั้นๆ ของสิ่งที่ทำในแต่ละไฟล์ต่อท้ายชื่อไฟล์ด้วยเครื่องหมายโคลอน `:` เสนออธิบายอย่างกระชับ
4. หากมีสถานะพิเศษ เช่น บอร์ดงานที่เสร็จสิ้น ให้ใส่ป้ายสถานะ (Badge) ต่อท้ายด้วยกล่องหรือตัวอักษร เช่น `🟢 Done`
5. หลังจากแสดงสรุปรายการไฟล์ที่เกี่ยวข้องแล้ว ให้พิมพ์สรุปผลลัพธ์ภาพรวมแบบสั้นๆ กระชับๆ ของส่วนงานที่ทำมา (Short Summary of Results) ต่อท้ายด้วยเสมอ

## 2. ขั้นตอนและแนวทางปฏิบัติการทดสอบจริง (Simulation Procedure)

เมื่อได้รับมอบหมายให้ **"ทดสอบระบบจริงในฐานะผู้ใช้งาน/จำลองระบบ"** ให้ดำเนินงานดังนี้:
1. **การจำลองสิทธิ์การเข้าทำรายการ**:
   * การจำลองผ่าน Code ให้เขียนสคริปต์ Node.js (mjs) โดยใช้บัญชีทดสอบที่กำหนดเพื่อรักษาความสะอาดและป้องกันข้อมูลจริงของลูกค้ารั่วไหล
   * หลีกเลี่ยงการเขียนข้อมูลใหม่ระรานบัญชีพาร์ทเนอร์/ช่างคนอื่นในระบบ ให้เจาะจงใช้งานบนโปรไฟล์ของ `ai.tester` และ `ai.manager` เท่านั้น
2. **การทำธุรกรรมและการหักเครดิต**:
   * ทดสอบจำลองแต้มโฆษณา (Impressions/Clicks) โดยคำนวณอัตราแต้มตรงตามตัวแปร config จริงเสมอ
   * ตรวจสอบว่าหลังจากทำรายการใดๆ จะต้องมีการเพิ่มบันทึกลงคอลเลกชันประวัติการทำธุรกรรม (`credit_transactions`) ด้วยทุกครั้ง
3. **การล้างข้อมูลขยะ (Cleanup)**:
   * หลังรันชุดทดสอบความถูกต้องเสร็จสิ้น หากมีสคริปต์ชั่วคราวที่สร้างขึ้นในโปรเจกต์ ให้ทำการลบสคริปต์เหล่านั้นทิ้งเพื่อไม่ให้รกพื้นที่ Repository หรือเกิดการหลุดรอดไปใน Production
